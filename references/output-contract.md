# 8 份精炼飞书稿改写契约

## 目标

详细源用于保留事实，飞书稿用于快速理解。改写不是按比例压缩原文，而是重新回答新人最关心的问题。

| 详细事实源 | 飞书稿需回答 |
|---|---|
| `STACK.md` | 项目用什么技术，哪些是核心依赖，新人需要先安装什么 |
| `STRUCTURE.md` | 核心代码在哪，不同目录大致管什么，改功能通常从哪里入手 |
| `ARCHITECTURE.md` | 系统有哪些主要部分，它们怎么配合，一次典型调用怎么走 |
| `CONVENTIONS.md` | 新人写代码时最容易违反的约定，提交前要注意什么 |
| `INTEGRATIONS.md` | 项目依赖哪些外部系统，失败时会影响什么，先查哪里 |
| `TESTING.md` | 如何跑最常用的测试，修改后至少验证什么 |
| `CONCERNS.md` | 当前最值得警惕的风险、未知项和需要询问维护者的事 |
| `ARCHITECTURE_DEEP_DIVE.md` | 用一个稍完整的视角串起核心边界、关键流程和排障入口 |

## 推荐写法

每篇可按以下顺序组织，但不要为套模板增加空洞章节：

1. 用一到两段说清这部分管什么、为什么存在，以及它和项目其他部分的关系。
2. 列出 4–6 个最值得记住的结论，每个结论补一句“这对新人意味着什么”。
3. 用一个项目中真实的小例子解释抽象机制，包含入口、发生的事、可观察结果和失败时先查哪里。
4. 给出少量关键文件或命令，解释它们为什么值得先看，并给出下一篇阅读或排障建议。

例如，不要只写“请求经过 controller、service 和 repository”；可以写成：“把一次请求想成去窗口办事：入口先检查材料，核心模块按规则处理，数据层负责保存结果。如果修改入参，先从 `routes/...` 开始追。”

## 取舍

- 保留：项目用途、主要边界、关键流程、开发入口、最重要的风险和必要的图。
- 压缩：长目录、类/函数清单、重复证据、每个配置项的细节。
- 删除：对新人心智模型没有帮助的实现细节、空洞的通用建议和机器控制标记。
- 保守表达：事实不明时写 `UNKNOWN` 或 `ASK MAINTAINER`，不靠经验补齐。

00–06 每篇约 600–900 个中文字，07 架构深读约 900–1400 字。这些只是帮助避免内容过薄的写作参考，不做机器验收。图的数量同样不设上限或下限：能让关系更直观就保留，否则用短文本。
