# 新人友好型项目 Onboarding 设计

## 目标与读者

目标读者是有开发经验、但不了解当前项目和业务领域的工程师。文档既要保留可验证的技术事实，也要让读者无需预先掌握项目术语，就能理解系统解决什么问题、一次真实操作如何流经系统，以及修改或排障应该从哪里开始。

成功标准：新人只阅读飞书文档，就能用自己的话回答项目用途、主要模块、核心链路、开发方式和常见排障入口；遇到专业术语时，能从紧邻解释和项目实例理解其作用。

## 采用方案

采用“分层讲解 + 确定性验证”。不生成第二套重复文档，也不只依赖提示词要求模型写得通俗。

每个飞书节点按以下顺序组织：

1. `30 秒看懂`：说明这一主题解决什么问题、在项目中扮演什么角色、新人为什么需要关注。
2. `项目中的真实例子`：使用当前仓库能够验证的入口、输入、处理过程、结果和失败检查点。
3. `实际工作机制`：在读者已有直观认识后，解释模块协作、数据变化和技术约束。
4. `代码在哪里`：给出真实代码、配置或测试证据。
5. `开发和排障怎么用`：说明修改前先确认什么、故障时先检查什么。

技术准确性优先于类比。类比只能帮助建立第一印象，后面必须紧接真实职责和边界，不允许用类比代替项目事实。

## 内容契约

### 新人摘要

00–07 每个飞书验证源文件都包含一个：

```markdown
<!-- newcomer-summary -->
用 60～180 个中文字符说明：这部分解决的问题、它在项目中的角色，以及新人为什么需要了解。
```

摘要不得只是目录说明、技术名词列表或章节内容复述。07 架构深读也必须有整体摘要。

### 真实项目示例

关键主题使用结构化示例：

```markdown
<!-- newcomer-example: submit-task -->
**场景**：调用方提交一个真实任务时，会提供哪些关键输入。

**发生了什么**：系统依次经过哪些真实模块，关键状态如何变化。

**结果**：调用方最终看到什么成功结果；失败时会看到什么。

**先查哪里**：排障时先检查哪个入口、日志、配置、状态或测试。

证据：path/to/file:line
```

示例 id 使用小写字母、数字和连字符。示例必须来自当前项目，不能套用与项目无关的“用户下单”等通用故事。

最低覆盖要求：

- 00 项目总览：至少一个端到端项目场景。
- 01 系统架构：每个重要 subsystem 至少被一个示例覆盖。
- 02 核心业务链路：每个 `core_flow` 恰好对应一个主要示例。
- 03 代码地图：至少一个“需求从入口定位到实现与测试”的示例。
- 05 开发与测试指南：至少一个本地修改、验证或排障示例。
- 07 架构深读：每个重要 subsystem 至少有一个真实使用或故障场景；可复用 01 中的示例 id，但正文必须适合当前上下文，不能只放引用。

04 和 06 在项目存在足够证据时加入示例；如果没有可验证场景，不为满足数量虚构内容。

### 术语与类比

项目特有或架构术语首次出现时继续使用 `<!-- term: id -->`，正文使用“通俗中文名称（技术名称）”格式，并解释它解决的问题及在本项目中的作用。

允许使用“像前台分诊”“像待发件箱”等短类比。类比段必须同时包含真实技术职责，且不得暗示项目并不存在的行为。

## 确定性验证

验证器新增以下检查：

1. 00–07 各有且仅有一个 `newcomer-summary`，长度符合要求；因为 07 必须完整复制架构深读，所以该标记同时存在于 `ARCHITECTURE_DEEP_DIVE.md`。
2. 每个 `newcomer-example` id 合法且在同一文件内唯一。
3. 每个示例紧邻并包含四个可识别字段：场景、发生了什么、结果、先查哪里。
4. 四个字段分别达到最低有效长度，不能重复同一段话。
5. 每个示例后有相邻证据行，证据路径必须存在。
6. profile 中每个 `core_flow` 在 02 中使用相同 id 的示例；每个重要 subsystem 在 01 和 07 中使用相同 id 的示例。id 可跨文件复用，但同一文件内必须唯一。
7. 00、03、05 满足各自最低示例要求。
8. 发布净化投影与验证源码确定性一致，且不会包含新增控制标记。

验证器不尝试用词频或“专业词密度”判断文风，因为这种判断容易误伤正常技术内容。通俗程度通过强制的摘要、术语解释、真实示例和新人七问共同约束。

## 新人七问复核

现有七问继续保留，并新增结构化证据：每个答案记录使用了哪些 `newcomer-summary` 或 `newcomer-example` id。复核从八份带标记验证源文件取得 id，但答案只能依据对应的用户可见正文；净化标记不承载事实，因此不得从源码或其他文件补充正文中没有的信息。

若问题只能复述技术名词、不能说明实际场景和开发者行动，则该问题不得标记通过。

## 飞书发布与净化

`docs/onboarding/lark/` 保留所有验证标记。`prepare_lark_publish.py` 新增删除：

- `<!-- newcomer-summary -->`
- `<!-- newcomer-example: id -->`

实际摘要和示例正文必须完整保留。`docs/onboarding/.lark-publish/` 仍是唯一上传来源。schema v3 双哈希、白板数量、降级码与回读检查保持不变。

## 失败处理

- 架构深读缺少摘要或示例：`local` 返回硬错误；00–07 缺少摘要、示例字段、覆盖关系或证据：`lark-ready` 返回硬错误。
- 净化投影过期或仍有控制标记：禁止发布。
- 项目没有某类能力：根据 profile 跳过对应示例，不制造虚假业务故事。
- 无法验证业务意图：使用 `ASK MAINTAINER`，并用已知事实说明问题边界。

## 测试策略

采用测试驱动实现：

1. 先加入缺失/重复摘要、摘要过短的失败测试。
2. 加入示例缺字段、重复字段、短内容、无证据和虚假路径测试。
3. 加入 `core_flow`、subsystem 与固定节点覆盖失败测试。
4. 加入净化测试，证明控制标记被删除而正文完整保留。
5. 更新现有 service、CLI、library、monorepo 测试夹具，证明契约对不同项目类型通用。
6. 运行完整单元测试、Python 编译、差异格式检查，并保留现有 Mermaid/Whiteboard 回归测试。

## 非目标

- 不把文档降级为面向零编程基础读者的教程。
- 不生成独立“新人版”和“专家版”两套重复内容。
- 不强制每个章节使用类比。
- 不用固定业务模板替代仓库事实。
- 不减少架构证据、图表、风险和技术细节，只调整信息出现顺序并增加理解桥梁。
